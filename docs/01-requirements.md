# Ice-Link 기능 요구사항

> 2026 KOSSCCHTHON · 주제 "교류" · 아이스브레이킹 앱
> 프론트 Flutter / 백엔드 Spring Boot 4.1.1 (Java 25) / DB PostgreSQL 18.6

---

## 1. 서비스 개요

처음 만난 사람들이 모인 자리(동아리 OT, 해커톤, 세미나 등)에서 **주최자**가 방을 만들고, **참가자**가 코드로 입장해
성격·관심사 설문을 하면 서버가 **관심사가 비슷한 사람끼리 팀을 구성**하고, 팀 단위로 **AI가 생성한 대화 질문**을 순차적으로 제공해
자연스럽게 대화를 이끌어 주는 서비스.

### 1.1 핵심 가치
- 로그인 없이 코드 입력만으로 즉시 참여 (진입 장벽 최소화)
- 같은 관심사 카테고리 안에서 외향/내향 점수 평균이 팀마다 비슷해지도록 나누는 팀 빌딩
- 팀의 실제 대화 내용(기기에서 음성→텍스트 변환)을 반영해 관심사 카테고리와 연관된 후속 질문을 생성하는 **적응형 대화 흐름**

### 1.2 사용자 식별과 역할

회원가입/로그인 없음. 앱 최초 기동 시 **이름을 입력**해 서버로 보내면 **서버가 유저 키를 생성**해 돌려주고, 클라이언트는 이를 기기에 저장한다. 이 값이 `users` 테이블의 PK가 된다.

```
userKey = lowercase_hex( 256-bit CSPRNG )   // 서버가 SecureRandom 으로 생성, 64자 hex. 이름과 무관
```

- 유저 키는 모든 요청에 `X-User-Key` 헤더로 전송되며, 이것이 곧 인증 수단이다.
- 키는 이름에서 유도하지 않는 순수 난수라 이름을 알아도 추측할 수 없고, 같은 이름이 몇 명이든 등록된다. 이름은 표시용이다.
- 이름은 이후 변경할 수 있으며 키는 바뀌지 않는다.
- 역할은 **방 단위**로 결정된다. 방을 만든 유저가 그 방의 주최자, 코드로 들어온 유저가 참가자다. 한 유저가 A방 주최자이면서 B방 참가자일 수 있다.

| 역할 | 설명 | 판정 |
|---|---|---|
| 주최자 (HOST) | 방을 만들고 팀 빌딩·진행을 제어 | `rooms.host_user_id == userKey` |
| 참가자 (PARTICIPANT) | 코드로 입장해 설문 후 팀 활동 | `participants(room_id, user_id)` 존재 |

**알려진 한계 (의도적으로 수용)**
- 일회성 서비스이므로 키는 기기에만 있고 복구 수단이 없다. 앱 삭제·기기 변경 시 새 이름 입력으로 새 유저가 된다.
- 기기 하나에 유저 하나다.
- SSE 는 헤더를 붙일 수 없어 `?userKey=` 쿼리를 허용한다. 접근 로그에 키가 남을 수 있으므로 쿼리스트링은 로그에서 제외한다.
- 방 코드(6자)는 추측 가능한 공간이므로 참가 API 에는 IP 기준 rate limit 을 두는 것이 바람직하다 (미구현).

## 2. 전체 흐름

```
[공통] 앱 최초 기동 → 이름 입력 → 서버가 난수 userKey 발급 → 기기 저장

[주최자]                                  [참가자]
방 생성 (상황 설정, 팀 인원수, 마무리 질문 목록)
  └─ 방 코드 / 초대 링크 발급
  └─ 링크·코드 공유 ───────────────────▶ 방 참가 (코드, 닉네임은 유저 이름 기본값)
                                          └─ 성격 질문 6개 (1~5점, 프론트 하드코딩)
                                          └─ 관심사 카테고리 1개 선택
                                          └─ 대기 화면 (참가자 수 실시간 표시)
참가자 현황 확인
참가 마감 + 팀 빌딩 실행 ─────────────────▶ 팀명(기본 "N팀") + 팀원 목록 표시
                                          └─ "팀원 만나는 중..." 화면
                                          └─ 팀원 모두 집합 → 세션 시작
팀 목록 / 팀명 / 진행 상황 모니터링 ◀────── Q1. 자기소개 + 팀명 정하기 → 기본 팀명 "N팀"을 수정
                                          └─ Q2. 공통 관심사 기반 AI 질문
                                          └─ 대답 음성 녹음 → 기기에서 STT → 텍스트 전송
                                          └─ 서버: 키워드 추출 → 카테고리 연관 Q3 생성 → ...
                                          └─ … (주최자가 종료할 때까지 반복)
아이스브레이킹 종료 버튼 (방 전체) ────────▶ 모든 팀 화면에 주최자 마무리 질문 목록 표시
                                          └─ 종료 화면 (마무리 질문, 팀명, 다룬 키워드 요약)
```

## 3. 기능 요구사항

표기: **[M]** 필수(MVP·시연 필수) / **[S]** 있으면 좋음 / **[C]** 시간 남으면

### 3.0 사용자 (User)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| U-01 | 앱 최초 기동 시 이름(1~12자)을 입력받아 서버에 보낸다. 클라이언트는 키를 계산하지 않는다 | [M] |
| U-02 | 서버는 `SecureRandom` 256-bit 난수를 64자 소문자 hex 로 만들어 `users`에 저장한 뒤 응답으로 돌려준다. 키는 이름과 무관하며 같은 이름이 몇 명이든 등록된다 | [M] |
| U-03 | PK 충돌(확률적으로 발생하지 않음)이 나면 `409 USER_KEY_CONFLICT`를 반환한다. 클라이언트는 같은 이름으로 재시도하면 된다 | [M] |
| U-04 | 서버는 `X-User-Key` 헤더 값의 형식(`^[0-9a-f]{64}$`)을 검증하고, 형식이 맞지 않으면 `400`, 등록되지 않은 키면 `401`을 돌려준다 | [M] |
| U-05 | 유저 키는 기기의 보안 저장소(`flutter_secure_storage`, Keychain/Keystore)에 저장하고, 이후 모든 요청에 `X-User-Key` 헤더로 보낸다 | [M] |
| U-06 | 유저는 이름을 변경할 수 있다. 키는 유지되며, 이미 참가 중인 방의 닉네임은 바뀌지 않는다 | [S] |
| U-07 | 앱 기동 시 저장된 키로 내 정보와 **현재 진행 중인 방**(FINISHED 아닌 가장 최근 참가/주최 방)을 한 번에 받아 화면을 복원한다 | [M] |
| U-08 | 유저는 자신이 주최/참가한 방 목록을 볼 수 있다 | [C] |
| U-09 | 미사용 유저(마지막 활동 30일 경과, 진행 중 방 없음)는 배치로 삭제한다 | [C] |

### 3.1 방 (Room)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| R-01 | 유저는 방을 생성할 수 있으며 생성자가 그 방의 주최자가 된다. 입력: 방 제목, 상황 설명(자유 텍스트, AI 질문 생성 컨텍스트로 사용), 팀당 인원수(2~10), **마무리 질문 목록**(선택, 0~5개, 각 200자) | [M] |
| R-02 | 방 생성 시 6자리 영문대문자+숫자 코드(혼동 문자 `0 O 1 I` 제외)와 초대 링크(`https://{host}/join/{code}` 및 딥링크 `icelink://join?code=`)가 발급된다 | [M] |
| R-03 | 방 상태는 `WAITING → TEAM_BUILDING → IN_PROGRESS → FINISHED` 순으로 전이한다 (역행 불가) | [M] |
| R-04 | 주최자는 방 정보(제목, 상황 설명, 팀 인원수)를 `WAITING` 상태에서만 수정할 수 있다. **마무리 질문 목록은 방이 종료되기 전까지 언제든 수정 가능** (진행 중 떠오른 질문을 추가할 수 있어야 함) | [S] |
| R-05 | 주최자는 주최자 화면의 "아이스브레이킹 종료" 버튼으로 방을 종료(`FINISHED`)한다. 종료 시 ① 모든 팀 세션이 함께 종료되고 ② 모든 참가자 화면에 **주최자 마무리 질문 목록이 표시**된다. 마무리 질문이 없으면 요약만 표시 | [M] |
| R-06 | 방은 생성 후 24시간 뒤 자동 만료(`FINISHED`)된다 | [C] |
| R-07 | 주최자는 방 정보와 참가자 현황(닉네임, 설문 완료 여부)을 조회할 수 있다 | [M] |
| R-08 | 주최자는 자기 방에 참가자로 동시에 들어갈 수 없다 (역할 혼동 방지). 시연 시 필요하면 다른 기기를 사용 | [M] |
| R-09 | 한 유저는 동시에 하나의 진행 중인 방(WAITING/TEAM_BUILDING/IN_PROGRESS)에만 참가자로 속할 수 있다. 다른 방 참가 시 `409` | [M] |

### 3.2 참가 (Participant)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| P-01 | 유저는 방 코드를 입력해 입장한다. 방 내 닉네임(1~12자)은 유저 이름이 기본값이며 입장 시 바꿀 수 있다. `WAITING` 상태의 방에만 입장 가능 | [M] |
| P-02 | 같은 방 안에서 닉네임은 중복될 수 없다 (대소문자 무시). 중복이면 거절하지 않고 **서버가 `민수2`, `민수3` … 으로 자동 변경해 저장**하며, 응답의 `nickname`으로 확정된 값을 알려준다. 후보(2~99)가 모두 쓰인 경우에만 `409` | [M] |
| P-03 | 같은 유저는 한 방에 한 번만 참가할 수 있다 (`UNIQUE(room_id, user_id)`). 이미 참가 중인 방에 다시 입장 요청하면 기존 참가 정보를 `200`으로 돌려준다 (멱등). 나간 뒤(`LEFT`) 재입장하면 같은 행을 `JOINED`로 재활성화하고 설문은 초기화한다 | [M] |
| P-04 | 참가자는 팀 빌딩 전까지 방에서 나갈 수 있다 (soft delete) | [S] |
| P-05 | 참가자 상태: `JOINED → SURVEY_DONE → ASSIGNED` | [M] |
| P-06 | 방 인원 상한 100명. 초과 시 입장 거절 | [S] |

### 3.3 설문 (Survey)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| S-01 | 성격 질문 6개의 **문항 텍스트는 프론트에 하드코딩**한다. 서버는 문항 번호(1~6)와 점수만 받고 텍스트는 다루지 않는다 | [M] |
| S-02 | 각 문항은 5점 리커트 척도로 응답한다. `5 = 매우 그렇다(높음)` ~ `1 = 전혀 그렇지 않다(낮음)`. 6문항 모두 외향성을 측정하며, 합산 **외향 점수는 6~30**이다. 높으면 외향, 낮으면 내향 | [M] |
| S-03 | 관심사 카테고리 5개(`MOVIE, GAME, FOOD, TRAVEL, SPORTS`) 중 **정확히 1개**를 선택한다 | [M] |
| S-04 | 성격 답변과 카테고리는 한 번의 요청으로 제출하거나 나눠서 제출할 수 있으며, 둘 다 완료되면 참가자 상태가 `SURVEY_DONE`이 된다 | [M] |
| S-05 | 설문은 팀 빌딩 전까지 재제출(덮어쓰기) 가능 | [S] |
| S-06 | 서버는 문항 번호 1~6이 정확히 6개, 점수 1~5 범위임을 검증한다. 문항 번호 집합이 바뀌면 프론트·백 동시 배포가 필요하므로 번호는 고정 | [M] |

**성격 질문 (참고용, 프론트 하드코딩. 서버는 번호만 인지)**

| # | 질문 |
|---|---|
| 1 | 나는 함께 있는 것을 좋아한다 |
| 2 | 나는 새로운 사람들과 만나는 것이 편하다 |
| 3 | 나는 파티나 모임에서 주도적으로 대화를 이끈다 |
| 4 | 나는 사람들과 함께 있을 때 에너지를 얻는다 |
| 5 | 나는 많은 사람들과 친구로 지내는 것을 선호한다 |
| 6 | 나는 생각하기 전에 먼저 말하는 편이다 |

외향 점수 해석(표시용): `6~13 내향` / `14~22 중간` / `23~30 외향`

### 3.4 팀 빌딩 (Team Building)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| T-01 | 주최자가 팀 빌딩을 실행하면 참가 마감 후(`TEAM_BUILDING`) 알고리즘이 돌고 완료 시 `IN_PROGRESS`로 전이한다 | [M] |
| T-02 | 설문 미완료 참가자(`JOINED`)는 팀 빌딩에서 제외되고, 이후 `LATE` 상태로 주최자가 수동 배치할 수 있다 | [S] |
| T-03 | 팀은 **같은 카테고리를 선택한 참가자끼리** 구성한다. 카테고리별로 독립적으로 팀을 나눈다 | [M] |
| T-04 | 카테고리 그룹 인원 `n`, 팀당 인원 `s`일 때 팀 수 `k = max(1, round(n / s))`. 인원은 팀 간 최대 1명 차이가 나도록 균등 배분한다 (예: n=11, s=4 → 4/4/3) | [M] |
| T-05 | 각 카테고리 그룹 안에서 **팀별 외향 점수 평균이 서로 비슷**해지도록 배치한다. 외향 점수 내림차순 정렬 후 스네이크(serpentine) 배분을 기본으로 하고, 이후 팀 간 1:1 교환으로 평균 분산을 줄이는 개선 단계를 거친다 | [M] |
| T-06 | 카테고리 그룹 인원이 최소 팀 인원 `max(2, ceil(s/2))` 미만이면 그 인원은 **잔여 인원**으로 두고, 전체 팀 중 인원이 가장 적은 팀에 1명씩 배치한다. 동률이면 그 참가자를 넣었을 때 팀 평균이 전체 평균에 가장 가까워지는 팀 | [M] |
| T-07 | 모든 카테고리가 최소 인원 미달이면(예: 5명이 5개 카테고리로 흩어짐) 카테고리를 무시하고 전체를 하나의 그룹으로 T-04/T-05 적용 | [M] |
| T-08 | 팀 번호는 1부터 순차 부여(카테고리 순 → 팀 순)하며, **팀명은 팀 번호로 자동 생성**된다 (`"1팀"`, `"2팀"` …). 팀에는 `category`(팀 구성 기준 카테고리)와 `mixed`(잔여 인원 포함 여부)를 저장한다. 잔여 인원이 섞여도 AI 질문은 팀 `category` 기준으로 생성 | [M] |
| T-09 | 참가자는 배정 결과(팀명, 팀원 닉네임 목록, 팀 카테고리)를 조회할 수 있다. 화면에는 팀 번호 대신 팀명을 표시한다. 외향 점수는 본인 것만 보이고 타인 점수는 노출하지 않는다 | [M] |
| T-10 | 주최자는 팀별 외향 점수 평균과 인원을 확인할 수 있다 (균형 확인용) | [S] |
| T-11 | 주최자는 팀 빌딩 결과를 확인하고, 필요 시 특정 참가자를 다른 팀으로 옮길 수 있다 (세션 시작 전까지) | [C] |
| T-12 | 주최자는 팀 빌딩을 재실행할 수 있다 (세션이 하나도 시작되지 않은 경우) | [C] |

### 3.5 팀 세션 (Team Session) – 아이스브레이킹 진행

| ID | 요구사항 | 우선순위 |
|---|---|---|
| Q-01 | 팀원은 "모두 모였어요" 버튼으로 세션을 시작한다. 팀 내 아무나 눌러도 되며, 이미 시작된 세션은 멱등 처리 | [M] |
| Q-02 | 세션 시작 시 1번 질문(고정): "자기소개를 하고 팀명을 정해보세요" 가 제시된다. 화면에는 현재 팀명(기본 `"N팀"`)이 편집 가능한 상태로 보인다 | [M] |
| Q-03 | 팀명은 별도 등록 절차 없이 **기본값 `"N팀"`을 수정하는 방식**이다. 팀원 누구나 1~20자로 바꿀 수 있고, 수정하지 않으면 `"N팀"`이 그대로 유지된다. 수정 즉시 주최자 화면의 팀 목록에 반영된다 | [M] |
| Q-03a | 같은 방 안에서 팀명은 중복될 수 없다 (대소문자·공백 무시). 중복이면 `409`. 빈 문자열로 수정하면 기본값 `"N팀"`으로 되돌린다 | [M] |
| Q-04 | 2번 질문(카테고리 기반 첫 질문)은 AI가 **프롬프트 ①**로 생성한다. 입력: 방의 상황 설명, 팀 카테고리, 팀원 수. 출력: 질문 텍스트 1개 (평문) | [M] |
| Q-05 | 각 질문에 대해 팀은 음성으로 답한다. **음성→텍스트 변환(STT)은 프론트(기기)에서 수행**하고, 서버에는 변환된 텍스트(1~3000자)만 전송한다. 음성 파일은 서버로 보내지 않고, 화자 구분도 하지 않는다 | [M] |
| Q-06 | 서버는 전달받은 대화 텍스트에서 키워드(3~7개)를 추출해 저장한다. 키워드는 꼬리질문 생성과 같은 호출에서 얻는다 | [M] |
| Q-07 | 다음 질문(꼬리 주제)은 AI가 **프롬프트 ②**로 생성한다. 입력: 상황 설명, 팀 카테고리, 팀원 수, 직전 질문, 대화 텍스트, 누적 키워드, 이 팀의 이전 질문 목록(팀 내 중복 방지). 출력: 키워드 3~7개 + **키워드를 소재로 팀 전체가 함께 이야기할 하나의 주제 질문**(첫 질문과 같은 형식) 1개 | [M] |
| Q-08 | AI 처리는 비동기이며, 질문 상태 `ANSWERING → PROCESSING → DONE` 으로 전이한다. 처리 실패 시 `FAILED` 로 두고 재시도를 허용한다. 재시도도 실패하면 카테고리 기본 질문 풀에서 다음 질문을 뽑아 흐름을 끊지 않는다 | [M] |
| Q-15 | 팀원 중 **한 명의 기기**가 대표로 질문을 보고 녹음해 텍스트를 보낸다. 같은 질문에 여러 기기가 보내면 먼저 도착한 것만 처리하고 나머지는 `409`로 거절한다. 텍스트에는 화자 표시가 없으며 서버도 누가 말했는지 추적하지 않는다 | [M] |
| Q-16 | 텍스트가 너무 짧거나(10자 미만) 의미 없는 경우 프롬프트 ②를 건너뛰고, 프롬프트 ①로 카테고리 기반 일반 질문을 생성한다 | [S] |
| Q-17 | 질문 중복 방지 범위는 **팀 안**이다. 같은 방의 다른 팀이 비슷한 첫 질문을 받는 것은 허용한다 | [M] |
| Q-09 | 팀은 답변 없이 "건너뛰기"로 다음 질문을 요청할 수 있다 (이 경우 관심사 기반 일반 질문 생성) | [S] |
| Q-10 | 팀 세션의 종료는 **주최자만** 결정한다. 팀 화면에는 종료 버튼이 없고, AI 질문은 주최자가 종료할 때까지 반복된다 (상한 Q-13 도달 시 "주최자의 종료를 기다려 주세요" 안내) | [M] |
| Q-11 | 주최자가 방을 종료하면 모든 팀이 `FINISHED`로 전이하고, 팀 화면은 즉시 **주최자 마무리 질문 목록**으로 전환된다. 마무리 질문은 화면에 표시만 하며 답변을 수집하지 않는다 (팀이 오프라인으로 대화) | [M] |
| Q-11a | 종료 시점에 `PROCESSING` 중이던 답변은 처리를 끝내 요약·키워드는 저장하되, 다음 질문은 생성하지 않는다 | [M] |
| Q-12 | 종료 화면에 마무리 질문 목록, 팀명, 진행한 질문 수, 누적 키워드를 함께 보여준다 | [S] |
| Q-13 | 세션당 AI 질문 수 상한 15개 (비용 보호) | [S] |
| Q-14 | 팀 세션 상태: `NOT_STARTED → NAMING → QUESTIONING → FINISHED`. `FINISHED` 전이는 방 종료로만 일어난다 | [M] |

## 6. 상태 전이 요약

**Room**
```
WAITING ──(팀빌딩 실행)──▶ TEAM_BUILDING ──(완료)──▶ IN_PROGRESS ──(종료/만료)──▶ FINISHED
                                        └─(실패)──▶ WAITING
```

**Participant**
```
JOINED ──(설문 완료)──▶ SURVEY_DONE ──(팀 배정)──▶ ASSIGNED
  │                         │
  └──(나가기)──▶ LEFT       └──(마감 후 미배정)──▶ LATE ──(수동 배치)──▶ ASSIGNED
```

     │                         │                       │

    │                            └──(실패)──▶ FAILED ──(재시도)──▶ PROCESSING

    └──(건너뛰기)──▶ SKIPPED

## 7. 시연 시나리오 (주최자 / 참가자 화면)

0. 모든 기기: 앱 첫 실행 → 이름 입력 → 유저 키 생성·등록 (한 번만, 이후 자동 복원)
1. 주최자: 방 생성 → 코드 `K7M3PQ` 화면에 크게 표시, QR/링크 공유
2. 참가자 A~F (6명, 팀당 3명): 코드 입력 → 닉네임 확인(기본값 이름, 중복 시 서버가 "민수2"로 자동 변경) → 6문항 1~5점 → 카테고리 1개 선택 → 대기 화면 (인원수 실시간 증가)
3. 주최자: 참가자 6명 설문 완료 확인 → 팀 빌딩 실행 → 팀 2개 표시 (시연에선 3명은 GAME, 3명은 FOOD를 고르게 유도하면 카테고리별 팀이 명확히 보임)
4. 참가자: 팀명("1팀")·팀원 표시 → "팀원 만나는 중" → 한 명이 "모두 모였어요"
5. 팀: Q1 자기소개 & 팀명 → "1팀"을 "감자전사"로 수정 → 주최자 화면 팀 목록의 "1팀"이 "감자전사"로 바뀜
6. 팀: Q2 (AI, 공통 관심사 기반) → 음성 녹음 (기기 STT로 실시간 텍스트 표시) → 텍스트 전송 → 처리 중 → Q3 등장 (직전 대화 키워드 + 카테고리 연결)
7. 주최자: 팀 진행 상황 확인 → (필요 시 마무리 질문 추가) → "아이스브레이킹 종료" 버튼
8. 참가자: 모든 팀 화면이 동시에 주최자 마무리 질문 목록으로 전환 → 팀별로 대화 → 요약 화면
