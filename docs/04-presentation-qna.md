# Ice-Link 발표 예상 질문·답변 (기술 중심)

> 2026 KOSSCCHTHON 5팀 · 발표 자료(`ICE-LINK` 10장)와 대본, 실제 코드를 대조해 정리
> 답변은 코드에서 확인된 사실 기준. 대본·슬라이드와 구현이 다른 부분은 ⚠ 로 표시 → 발표 전 대본을 맞추거나 답변을 준비할 것

## 0. 발표 전 점검 요약

| 항목 | 대본·슬라이드 | 실제 구현 |
|---|---|---|
| 소수 카테고리 처리 | 다음 부족 카테고리에 병합 | 잔여 인원을 인원 최소 팀에 평균 기준으로 배치 (`mixed` 표시) |
| 동시 제출 방어 | 낙관적 락 | 낙관적 락 + 팀 행 비관적 잠금(`SELECT ... FOR UPDATE`) |
| 대화 원문 파기 | 방 종료 후 7일 자동 파기 | 정책만 정의, 삭제 배치 미구현 |
| 유저 키 | SHA-256(이름 + nonce) | **256-bit 난수 키로 변경됨** → 슬라이드 8 문구 수정 필요 |
| rate limit | 언급 없음 | 명세(참가 API IP 제한)만 있고 미구현 |
| 시연 클라이언트 | Flutter 앱 | 시연 영상은 React 웹 (아래 7절) |

## 1. 팀 빌딩 알고리즘

**Q. 팀 수와 인원은 어떻게 정합니까? 인원이 딱 안 나눠지면요?**
카테고리 그룹 인원 n, 팀당 인원 s일 때 팀 수 k = max(1, round(n/s)). 스네이크 배분이라 팀 간 인원 차이는 최대 1명. 예: 11명·4명 팀 → 3팀, 4/4/3. 그룹 인원이 최소 팀 인원 max(2, ceil(s/2)) 미만이면 팀을 만들지 않고 잔여 인원으로 돌린다.

**Q. 스네이크 배분만으로 균형이 보장됩니까?**
아니다. 스네이크는 초기 해이고, 이후 최대 20회 개선 단계를 돈다. 평균이 가장 높은 팀 H와 가장 낮은 팀 L을 골라, 1:1 교환 중 |avg(H') − avg(L')| 를 가장 크게 줄이는 쌍을 교환하고 개선이 없으면 즉시 종료. 순수 함수(`TeamBuilder`)로 분리해 단위 테스트 13건으로 결정성과 균형을 고정했다.

**Q. ⚠ 인원이 부족한 카테고리는 어떻게 처리합니까?**
대본은 "다음으로 인원이 부족한 카테고리에 병합"이지만 실제 구현은 다르다. 소수 그룹 구성원은 잔여 인원으로 두고, 이미 만들어진 팀 중 **인원이 가장 적은 팀들** 가운데 그 사람을 넣었을 때 팀 평균이 **전체 평균에 가장 가까워지는 팀**에 한 명씩 배치한다. 해당 팀에는 `mixed` 플래그를 남기고, AI 질문은 팀의 원래 카테고리로 생성한다. 모든 카테고리가 소수이면 카테고리를 무시하고 전체를 한 그룹으로 나눈다. → 대본을 이 설명으로 수정 권장.

**Q. 시간 복잡도는?**
정렬 O(n log n) + 스네이크 O(n) + 개선 O(20·s²). 100명(방 정원) 기준 1ms 미만.

**Q. 6문항 1~5점 설문이 외향성을 측정한다는 근거가 있습니까?**
검증된 심리 척도는 아니다. 목적이 개인 분류가 아니라 **팀 간 평균을 비슷하게 맞추는 상대적 균형**이므로 자기보고 점수(6~30)를 배분 지표로만 쓴다. 개인 점수는 본인에게만 노출하고, 주최자에게는 팀별 평균만 보여 준다.

**Q. 관심사를 임베딩/클러스터링 대신 고정 5개 카테고리로 한 이유는?**
참가자가 3분 안에 끝내야 하고 결과를 주최자가 설명할 수 있어야 한다. 고정 카테고리는 결정적·설명 가능하며 AI 프롬프트 가드레일의 기준으로도 그대로 쓰인다. 자유 텍스트 관심사 + 임베딩 매칭은 확장 과제.

**Q. 설문을 안 끝낸 참가자는?**
팀 빌딩 시 `LATE` 상태로 제외. 주최자가 옵션(`includeIncompleteSurvey`)을 켜면 포함되며, 점수 없으면 중간값 18점, 카테고리 없으면 잔여 인원 처리. 주최자의 수동 팀 이동은 명세만 있고 미구현.

## 2. AI 파이프라인

**Q. 요약·키워드·후속 질문을 한 번의 호출로 합쳤는데 출력 품질은 어떻게 보장합니까?**
JSON 모드로 `{"keywords":[...],"nextQuestion":"..."}` 한 줄만 출력하도록 강제하고, 응답에서 첫 `{`~마지막 `}`를 잘라 파싱한다. 파싱 후 질문이 1~200자인지, 팀 내 이전 질문과 중복되지 않는지 검사(`isUsable`)하고 실패하면 카테고리별 기본 질문 풀(50개)에서 뽑는다. `max_tokens`는 400에서 JSON이 잘리는 것을 확인해 700으로 상향.

**Q. STT 텍스트에 화자 구분이 없는데 AI가 특정인을 지목하면?**
프롬프트에 "팀원 한 명의 기기로 녹음되어 누가 말했는지 알 수 없다"를 명시하고 개인 지목·이름 호출을 금지. 항상 팀 전체에게 묻는 형태로 생성하고, 대화가 카테고리를 벗어나면 카테고리와 키워드를 **연결**하라는 규칙을 둔다 (예: GAME 팀 + 음식 키워드 → 밤샘 게이밍 야식).

**Q. 참가자가 프롬프트 인젝션을 시도하면?**
발화 텍스트는 사용자 메시지 영역의 데이터로만 들어가 시스템 지시와 분리된다. 출력은 JSON 스키마·길이·중복 검사를 통과해야만 쓰이고 실패 시 기본 질문으로 대체되므로 임의 텍스트가 그대로 화면에 나오는 경로가 없다. 단, 별도 유해성 필터는 없고 프롬프트 금지 규칙(정치·종교·외모·연봉·연애·신상)에 의존한다.

**Q. 비용은 얼마나 들고 어떻게 제어합니까?**
게이트웨이 크레딧 40달러. 팀당 질문 상한 15개, 호출당 최대 700 토큰, 입력은 직전 답변 1개 + 누적 키워드 + 이전 질문 목록만 전달해 토큰 절약. 호출마다 `usage.total_tokens`를 `generation_context`(jsonb)에 저장해 추적.

**Q. LLM이 느리거나 실패하면 사용자 경험은?**
호출은 트랜잭션 커밋 후 비동기 스레드(`@Async`, core 4 / max 8 / queue 100)에서 실행되고 답변 제출은 즉시 202. 연결 3초 / 읽기 15초 타임아웃, 타임아웃·5xx는 1초 후 1회 재시도. 그래도 실패하면 질문을 `FAILED`로 두고 SSE `ANSWER_FAILED` 통지 → 사용자는 재시도 또는 건너뛰기, 재시도도 실패하면 기본 질문 풀로 진행.

**Q. 왜 STT를 서버가 아니라 기기에서 합니까?**
행사장 네트워크에서 오디오 업로드가 가장 큰 병목이고, 음성 원문을 서버에 두지 않는 것이 프라이버시에도 유리하다. 텍스트만 오므로 서버는 3000자 상한만 검증. 단점은 기기별 인식 품질 차이와 화자 분리 불가.

**Q. 모델 선택 이유는?**
국민대 AI 게이트웨이(OpenAI Chat Completions 호환)에서 발급 키가 접근 가능한 모델이 `claude-opus-5` 하나였다(다른 모델은 403). 한국어 개방형 질문 품질은 충분했고, 비용은 상한·토큰 제한으로 통제.

## 3. 실시간 동기화와 동시성

**Q. 왜 WebSocket이 아니라 SSE입니까?**
서버→클라이언트 단방향 알림만 필요하고 조작은 REST로 충분. SSE는 브라우저가 자동 재연결과 `Last-Event-ID` 재전송을 기본 제공한다. 이벤트를 `room_events` 테이블에 저장하고 DB id를 seq로 써서 재연결 시 누락분을 서버가 재전송. 접속 직후 `CONNECTED` 이벤트로 현재 seq 전달, 15초 하트비트, 30분 타임아웃.

**Q. 브로드캐스트 시점은?**
도메인 트랜잭션 **커밋 후**(`afterCommit`). 커밋 전에 보내면 클라이언트가 이벤트를 받고 REST로 조회했을 때 반영 전 상태를 보기 때문.

**Q. 서버가 여러 대면?**
현재 SSE 레지스트리가 인메모리라 단일 인스턴스 전제. 스케일아웃 시 Redis Pub/Sub 등 팬아웃 계층이 필요하며, `room_events`가 있어 재연결 리플레이는 그대로 재사용 가능.

**Q. 개발 중 겪은 실시간 관련 문제는?**
브라우저는 HTTP/1.1에서 호스트당 연결 6개 제한이 있는데 SSE가 연결을 점유해, 한 PC에서 탭을 여러 개 열면 일반 요청이 대기 끝에 타임아웃됐다. 테스트 환경에서는 SSE를 다른 호스트명으로 보내 연결 풀을 분리했고, 운영에서는 HTTPS + HTTP/2 다중화가 정답.

**Q. 팀원 여러 명이 동시에 답변을 보내면?**
질문 상태 전이(ANSWERING→PROCESSING)와 `@Version` 낙관적 락으로 두 번째 제출은 409. 여기에 더해 세션 시작·다음 질문·답변 제출 진입 시 팀 행을 `SELECT ... FOR UPDATE`로 잠가 같은 팀의 동시 요청이 순서대로 처리된다. 실제로 4명이 동시에 시작을 눌러 `(team_id, order_no)` 유니크 위반 500이 났던 문제를 이 방식으로 해결. ⚠ 슬라이드에는 낙관적 락만 적혀 있으니 비관적 잠금을 함께 언급.

**Q. 비동기 AI 작업이 유실되면 세션이 멈추지 않습니까?**
알고 있는 한계. 다음 질문 요청 시 현재 질문을 건너뜀 처리하고 생성 태스크에 의존하므로, 서버 재시작·큐 포화로 태스크가 죽으면 열린 질문이 없는 상태가 된다. 개선안: 생성 대기 상태의 질문 행을 먼저 만들고 타임아웃 워커로 회수.

**Q. 세션 시작을 여러 명이 눌러도 됩니까?**
멱등. 첫 호출만 INTRO 질문을 만들고 이후 호출은 현재 상태를 그대로 반환(200). 팀명 변경도 팀원 누구나 가능하며 방 안 중복은 409.

## 4. 인증, 보안, 프라이버시

**Q. 로그인 없이 어떻게 사용자를 식별합니까? 안전합니까?**
이름을 보내면 서버가 `SecureRandom` 256-bit 난수를 64자 hex 로 만들어 돌려주고, 클라이언트가 기기 보안 저장소에 보관한다. 키는 이름과 무관한 순수 난수라 이름을 알아도 추측할 수 없고(후보 2²⁵⁶), 같은 이름이 몇 명이든 등록된다. 키는 `X-User-Key` 헤더로 모든 요청에 실리고, 호스트/참가자 권한은 방 단위로 DB에서 판정. 일회성 서비스라 복구 수단은 두지 않았고, 기기를 바꾸면 새 이름으로 다시 들어오면 된다.

**Q. 처음 설계는 SHA-256(이름+nonce) 였다고 들었는데 왜 바꿨습니까?** (초기 명세를 본 심사자가 물을 수 있음)
초기 설계는 nonce 가 1~100 이라 이름당 키 후보가 100개뿐이어서, 이름을 알면 100번 시도로 키를 찾을 수 있었다. 가벼운 서비스라 수용했지만 실제 배포를 고려해 난수 키로 바꿨다. 서버 함수 하나와 등록 로직만 바뀌고 헤더·형식·클라이언트는 그대로다.

**Q. 이름이 같은 사람이 많으면?**
제한 없다. 이름은 표시용이고 키가 식별자다. 방 안 닉네임 중복은 서버가 "민수2"처럼 자동 변경.

**Q. SSE는 헤더를 못 붙이는데 인증은?**
`?userKey=` 쿼리 파라미터 허용. 접근 로그에 남을 수 있어 운영에서는 짧게 만료되는 스트림 전용 토큰으로 교체 필요.

**Q. ⚠ 대화 원문은 언제 삭제됩니까?**
대본·슬라이드는 "방 종료 후 7일 자동 파기"지만, 현재 코드는 방 만료 시각(`expiresAt`)을 저장할 뿐 삭제 배치가 없다. 정책은 확정, 구현은 후속. 질문이 나오면 "정책 확정, 삭제 스케줄러는 후속 구현"으로 답하거나 발표 전 표현을 "파기 정책 수립"으로 조정. 수집 항목이 이름·닉네임·설문 점수·대화 텍스트뿐이고 음성 파일·연락처는 서버에 오지 않는다는 점은 그대로 강조 가능. 대화 원문은 로그에 남기지 않는다(API 로그도 `answerText`를 마스킹).

## 5. 아키텍처와 데이터

**Q. 전체 구조를 설명해 주세요.**
Spring Boot 4.1 / Java 25 / PostgreSQL 18 / JPA. 도메인별 수직 슬라이스 패키지(user, room, participant, survey, team, ai, realtime). room이 participant·team을 직접 참조하지 않도록 포트 인터페이스(`RoomParticipantQuery`, `RoomTeamQuery`)를 두어 의존 방향을 끊었다. 상태 전이는 전부 엔티티 메서드 안에 있고 위반 시 409, 모든 에러는 RFC 9457 Problem Details로 통일.

**Q. 스키마 마이그레이션 도구를 안 쓴 이유는?**
백엔드 1인 개발과 일정 때문에 `ddl-auto=update`. 컬럼 변경·삭제를 처리하지 못하는 한계를 알고 있어 시연 직전 `validate`로 정합성 확인, 운영 전환 시 Flyway 도입.

**Q. jsonb는 어디에 썼습니까?**
방의 마무리 질문 목록, 답변 키워드 배열, 질문 생성 컨텍스트(프롬프트 입력값·토큰 수), SSE 이벤트 payload. 스키마가 자주 바뀌는 부가 데이터라 정규화보다 유연성.

**Q. 앱을 껐다 켜면 어디로 갑니까?**
`GET /users/me`가 진행 중인 방·역할·참가 상태·팀 ID를 함께 반환해 클라이언트가 첫 화면을 결정. 웹 버전은 홈의 "진행 중인 방으로 이동"으로 복귀.

**Q. 방 정원과 동시 방 수 기준은?**
방 100명, 동시 방 50개. 팀당 인원 2~10, 마무리 질문 최대 5개(200자), 팀당 질문 상한 15.

## 6. 테스트와 운영

**Q. 테스트는 어떻게 했습니까?**
단위·슬라이스 테스트 239건 전부 통과(도메인 전이, 서비스, `@WebMvcTest` 컨트롤러, 팀 빌딩 알고리즘, SSE 스코프 필터). 실 DB 통합 테스트는 없어, 로컬 백엔드에 대해 등록→종료 API 흐름, SSE 이벤트 수신, 4명 동시 요청 시나리오를 스크립트로 별도 검증.

**Q. 성능 목표와 실제는?**
일반 API p95 300ms 목표, AI 생성은 비동기 5~15초를 SSE로 통지. 팀 빌딩 100명 기준 1ms 미만.

**Q. 배포는?**
`java -jar` 단일 프로세스, 환경 변수 파일로 비밀값 주입, systemd 유닛 제공. 헬스체크는 actuator.

## 7. 클라이언트: Flutter 기획 vs React 시연

**Q. 기획은 Flutter 앱인데 시연 영상은 왜 React 웹으로 했습니까?**
이 서비스는 주최자 1명 + 참가자 여러 명이 **동시에** 참여해야 흐름이 보이는 다인용 서비스다. Flutter 앱은 스토어에 배포하지 않으면 여러 사람 기기에 올리기 어렵고, 해커톤 기간 안에 심사 통과·배포는 불가능하다. 개발자 모드 사이드로딩이나 TestFlight도 기기마다 별도 설정·등록이 필요해 시연용 기기 여러 대 준비가 어려웠다.

그래서 **백엔드 API를 그대로 호출하는 React 웹 버전**을 만들었다. 브라우저 탭마다 독립 사용자 세션이 되도록 설계해 한 PC에서 주최자와 참가자 4~5명을 동시에 띄우고, 팀 빌딩과 실시간 동기화를 한 화면에서 보여 줄 수 있다. 시연에서 왼쪽·가운데 탭이 같은 팀으로 배정되어 화면이 함께 넘어가는 장면이 그 결과.

웹 버전은 화면 계층만 다르고 API·인증·SSE 이벤트·팀 세션 규칙은 앱과 완전히 동일하다. 제품 본체는 Flutter 앱이고, 온디바이스 음성 인식처럼 기기 기능이 핵심인 부분도 앱 기준으로 설계됐다(웹은 브라우저 내장 음성 인식으로 대체).

부수 효과: 웹으로 여러 사용자를 동시에 돌려 보다가 팀원 동시 세션 시작 시 유니크 제약 위반(경쟁 조건)과 팀 세션 상태 규칙 불일치를 발견해 서버를 고쳤다. 다인용 서비스는 결국 여러 사용자를 동시에 돌려 봐야 검증되므로, 웹 버전은 시연용이자 **통합 테스트 도구** 역할을 했다.

**꼬리 질문**
- *Flutter 앱은 실제로 동작합니까?* 동작한다. 같은 API로 로그인·방 생성·참가·설문·팀 배정까지 연동되어 있고, 시연 영상만 다인 동시 시연이 가능한 웹으로 촬영했다.
- *웹으로 만들 거면 처음부터 웹으로 기획하지 않은 이유는?* 현장 사용성. 참가자가 자기 폰으로 코드를 입력하고 음성으로 답하는 흐름은 앱이 자연스럽고, 기기 내장 음성 인식은 네이티브 앱에서 품질·권한 처리가 안정적이다.
- *두 클라이언트를 유지하는 비용은?* 화면 계층만 두 벌이고 비즈니스 규칙은 전부 서버에 있어 중복이 적다. 웹은 테스트·시연 도구로 한정할 계획.
